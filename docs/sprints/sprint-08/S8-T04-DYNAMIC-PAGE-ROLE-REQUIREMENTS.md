## 1. Executive Summary & Architectural Governance

### 1.1 Purpose
This specification formalizes the **Dynamic-Page, Production-Context, and Role Authorization Requirements** for the Burra Pariksha Content Management System (BP-CMS). Building directly on the forensic baselines established in S8-T01 (Question Generation Audit), S8-T02 (Production Page & Workflow Inventory), and S8-T03 (Content Mode Requirements), and reconciled against the authoritative ID contract ([id.service.ts](file:///c:/Users/jithendra/OneDrive/Desktop/burra_pariksha_cms/shared/lib/id.service.ts)) and canonical role enum ([roles.ts](file:///c:/Users/jithendra/OneDrive/Desktop/burra_pariksha_cms/shared/constants/roles.ts)), this document defines:
1. The **Shared Production Context** propagated across all production workbenches.
2. The **Page-State Matrix** specifying the behavior of every in-scope canonical page and workbench across all six fundamental UI states (`loading`, `empty`, `error`, `read-only`, `incomplete`, and `completed`), including explicit draft resumption and recovery rules.
3. The **Role-to-Action Matrix** mapping the 11 canonical roles and atomic capabilities to page visibility, resource-scoped access, business preconditions, and **GAR-02 Anti-Self-Approval**.
4. The exact rules governing **direct-link hydration**, **draft resumption**, and **separation of Save Draft vs. Submit for Verification**.
5. The formal criteria for **Gate A**, which remains **BLOCKED** until S8-T01 through S8-T04 are formally accepted.

### 1.2 Core Architectural Invariants (Non-Negotiable)
Every requirement defined herein adheres strictly to the authoritative BP-CMS architectural principles:
- **Zero-Trust Server Authority**: Client-side UI controls, visibility rules, and disabled buttons are strictly advisory presentation layers. Every HTTP read and mutation must be independently authenticated and authorized by Express server middleware (`requireCapability`) evaluating the 12-step RBAC pipeline.
- **15 Canonical Sequential Stages**: The end-to-end educational production pipeline preserves all 15 canonical steps in strict sequence (Stage 01 Question Generation through Stage 15 Social Performance Analytics). No stage may be bypassed, skipped, or merged out of existence.
- **Cloud Firestore Sole Transactional Datastore**: All runtime entities (`questions`, `question_drafts`, `scripts`, `videos`, `thumbnails`, `social_reviews`, `publishing`, `analytics_snapshots`, `users`, `audit_logs`) persist exclusively to Cloud Firestore. Zero runtime persistence to Google Sheets.
- **Canonical Two-Tier Taxonomy**: Educational classification is strictly two-tier: **Topic** (`top_<uuid>` or legacy `TOP-*`) $\longrightarrow$ **Subtopic** (`sub_<uuid>` or legacy `SUB-*`). The legacy `Category` concept is permanently obsolete.
- **Collision-Resistant UUID Canonical IDs**: Entity IDs are distributed, stateless UUID v4 identifiers formatted as `<prefix>_<uuid>` generated by `shared/lib/id.service.ts`:
  - Question Draft: `dft_<uuid>` (via `generateDraftId()`, reconciled with S8-T01)
  - Content Master: `cnt_<uuid>` (via `generateContentMasterId()`; `BP-CNT-######` is classified as legacy display alias)
  - Question: `qst_<uuid>` (legacy `BP-Q-######` / `QST-###`)
  - Video: `vid_<uuid>` (legacy `BP-V-######`)
  - Script: `scr_<uuid>`
  - Thumbnail: `thm_<uuid>`
  - Social Review: `rev_<uuid>`
  - Publishing: `pub_<uuid>`
  - Analytics Snapshot: `anl_<uuid>`
  - Performance Intelligence / Insight: `spi_<uuid>`
  - User: `usr_<uuid>` (legacy `BP-USR-######` / `USR-###`)
  - Topic: `top_<uuid>` (legacy `TOP-###`)
  - Subtopic: `sub_<uuid>` (legacy `SUB-###`)
  - Workflow Instance: `wfl_<uuid>`
- **Save Draft $\neq$ Submit for Verification**: Saving a draft persists minimal valid fields to `question_drafts` without leaving the page or triggering verification. Submitting for verification is an explicit, deliberate user action that executes authoritative validation gates and advances the workflow from Stage 01 to Stage 02.
- **Anti-Self-Approval (`GAR-02`)**: No author may approve their own submission across review gates (Stage 02 Question Verification, Stage 07 Final QC, Stage 09 Social Review). This rule is an absolute mathematical and architectural invariant enforced server-side with zero role-based bypass, zero administrative exceptions, and zero emergency overrides across all roles, including `ADMIN`.
- **Documentation & Specification Only**: In strict compliance with Sprint 8 rules, this document provides architecture contracts and specifications. Zero application code, routes, or schema migrations may be executed prior to formal Gate A approval.

## 2. Shared Production Context Specification

### 2.1 Context Definition & Canonical Attributes
The **Shared Production Context** (`ProductionContext`) represents the unified operational envelope passed across all production workbenches. It binds the active curriculum domain, content format, persistence entities, workflow lifecycle, task assignment, and current actor authorization into a cohesive state.

```typescript
export interface ProductionContext {
  // 1. Curriculum Taxonomy (Authoritative Two-Tier)
  topicId: string;                     // Canonical Topic ID (e.g., 'top_a1b2c3d4-e5f6-4a7b-8c9d-0e1f2a3b4c5d' or legacy 'TOP-101')
  subtopicId: string;                  // Canonical Subtopic ID (e.g., 'sub_e5f6g7h8-a1b2-4c3d-9e0f-1a2b3c4d5e6f' or legacy 'SUB-201')

  // 2. Production Mode & Configuration (Traced to S8-T03)
  productionMode: ContentProductionMode; // QUESTION_CHALLENGE_SHORT | TOPIC_INTRODUCTION | EXPLAINED_QUESTIONS_VIDEO
  questionCount?: 5 | 10 | 15 | 20;    // Configurable question count; strictly prohibited in Mode 2

  // 3. Entity Identifiers & Aggregation (Reconciled with id.service.ts)
  contentId?: string;                  // Canonical Content Master ID: 'cnt_<uuid>' (Legacy display format: 'BP-CNT-######')
  draftId?: string;                    // Active Question Draft ID: 'dft_<uuid>' (Reconciled with S8-T01 & id.service.ts)
  entityId?: string;                   // Primary active stage entity ID: 'qst_<uuid>' | 'vid_<uuid>' | 'scr_<uuid>' | 'thm_<uuid>' | 'rev_<uuid>' | 'pub_<uuid>' | 'anl_<uuid>' | 'spi_<uuid>'

  // 4. Workflow Lifecycle & State
  workflowStage: number;               // Canonical step: 1 to 15
  stageStatus: WorkflowStageStatus;    // DRAFT | IN_PROGRESS | PENDING_REVIEW | CHANGES_REQUESTED | APPROVED | SCHEDULED | PUBLISHED | SYNCED | COMPLETED | TERMINATED

  // 5. Assignment & Ownership Context (Aligned with Canonical Roles & Assignment Roles)
  assignment: {
    ownerId: string;                   // Creator / initiator of the content record (usr_<uuid>)
    assignedAuthorId?: string;         // Author assigned to draft (Stage 01)
    assignedReviewerId?: string;       // Reviewer assigned to verification (Stage 02)
    assignedScriptwriterId?: string;   // Scriptwriter assigned to script (Stage 03)
    assignedPresenterId?: string;      // Studio talent assigned to filming (Stage 04)
    assignedEditorId?: string;         // Editor assigned to render cut (Stage 06)
    assignedQcLeadId?: string;         // QC reviewer assigned to Final QC (Stage 07)
    assignedDesignerId?: string;       // Graphic artist assigned to thumbnail (Stage 08)
    assignedPublisherId?: string;      // Publishing lead assigned to social review, publishing, and sync (Stages 09–12)
  };

  // 6. Authenticated Actor & Effective Capabilities
  actor: {
    id: string;                        // Authenticated User ID: 'usr_<uuid>' (Legacy format: 'BP-USR-######' or 'USR-001')
    name: string;                      // Display name
    roles: CanonicalRbacRole[];        // Assigned canonical roles (from CanonicalRbacRole enum)
    effectiveCapabilities: string[];   // Expanded set of 'RESOURCE:ACTION' capability tokens
    isAiAgent: boolean;                // Flag distinguishing automated bots from human actors
  };
}
```

### 2.2 Lifecycle & Context Propagation
Context flows continuously through the production journey across routes and components:

```text
  ┌────────────────────────────────────────────────────────────────────────────────────────┐
  │                           PRODUCTION CONTEXT PROPAGATION FLOW                          │
  └────────────────────────────────────────────────────────────────────────────────────────┘
    [Planning / Batch Initiation] (/planning)
       │ (Seeds topicId, subtopicId, productionMode, questionCount)
       ▼
    [Stage 01: Question Studio] (/studio?mode=...&topicId=...&subtopicId=...)
       │ (Generates draftId dft_<uuid>, questionId qst_<uuid>, creates WorkflowInstance wfl_<uuid>)
       ▼
    [Stage 02: Question Verification] (/questions/:id/verify?contentId=...)
       │ (Approve creates initial video stub vid_<uuid>, advances to Stage 03)
       ▼
    [Stages 03–08: Master Production Workbench] (/videos/:videoId?tab=script|recording|editing|final-review|thumbnail)
       │ (Carries contentId cnt_<uuid>, videoId vid_<uuid>, scriptId scr_<uuid>, thumbnailId thm_<uuid>; updates workflowStage)
       ▼
    [Stage 09: Social Review Studio] (/social-review/:reviewId?videoId=...)
       │ (Carries reviewId rev_<uuid>, videoId vid_<uuid>, thumbnailId thm_<uuid>; advances to Stage 10)
       ▼
    [Stages 10–12: Publishing & Sync] (/publishing?videoId=... -> /platform-packages/:videoId)
       │ (Carries publishing record pub_<uuid>, external platform IDs)
       ▼
    [Stages 13–15: Analytics & Intelligence] (/social-analytics/:contentId -> /analytics/intelligence)
       │ (Ingests snapshot anl_<uuid>, finalizes performance record spi_<uuid>, feeds directives back to Stage 01)
       ▼
    [Loopback / Archive] (WorkflowInstance wfl_<uuid> status = COMPLETED)
```

1. **URL Parameter Grounding**: The primary mechanism for cross-page context propagation is explicit URL query parameters (`?contentId=...&draftId=...&tab=...`). This guarantees that browser refreshes, shared links, and deep links preserve exact context without relying on transient React memory.
2. **Context Provider Hydration**: The frontend wraps production workbenches in a `ProductionContextProvider` that parses incoming URL parameters, validates session credentials, fetches authoritative server records from Cloud Firestore repositories, and exposes typed context hooks (`useProductionContext()`) to child components.
3. **Immutability of Key Attributes**: Once a content record enters Stage 02 (`PENDING_REVIEW`), `productionMode`, `topicId`, and `subtopicId` become immutable. They can only be modified if the item is rejected back to Stage 01 for comprehensive restructuring.

### 2.3 Direct-Link Behavior (Deep Linking)
When a user accesses any production workbench directly via URL (e.g., `/videos/vid_12345?tab=editing` or `/questions/qst_98765/verify`), the application executes a deterministic **5-Step Deep-Link Hydration Sequence**:

```text
 ┌────────────────────────────────────────────────────────────────────────────────────────┐
 │                         5-STEP DEEP-LINK HYDRATION SEQUENCE                            │
 └────────────────────────────────────────────────────────────────────────────────────────┘
   Step 1: Session Verification
           └── Extract session token from cookie/header. If unauthenticated -> Redirect to
               /login?returnUrl=<encoded_target_path>.
   Step 2: Entity & Workflow Fetch
           └── Retrieve primary entity and associated WorkflowInstance from Firestore API.
               If entity does not exist -> Render Canonical P-18 / 404 Not Found Page.
   Step 3: Stage-to-Route Validation
           └── Compare WorkflowInstance.currentStage with the target route/tab.
               • If matching -> Proceed to Step 4.
               • If out of sequence (e.g. attempting Stage 07 when video is at Stage 04) ->
                 Render Stage Mismatch Warning Banner with button to navigate to current stage.
   Step 4: Capability & GAR-02 Evaluation
           └── Check if actor possesses required RESOURCE:VIEW capability for the page.
               • If missing -> Render HTTP 403 Forbidden Access Page.
               • If present -> Evaluate GAR-02 for action controls (see Section 4.2).
   Step 5: Context Assembly & Workspace Render
           └── Populate ProductionContext, clear loading skeletons, and render active workbench.
```

### 2.4 Draft Resumption & Restoration of Saved State
Draft resumption must strictly prevent data loss, eliminate accidental stage jumps, and ensure seamless authoring continuity:

1. **Stage 01 Draft Resumption**:
   - Navigating to `/studio?draftId=dft_<uuid>` fetches the draft from the `question_drafts` Firestore collection.
   - Restores: `topicId`, `subtopicId`, `productionMode`, `questionCount`, Telugu question stem, options array (indices 0–3), correct answer index, explanation, and mathematical proof steps.
   - Clears the dirty state flag (`isDirty = false`).
   - The UI indicates *"Draft restored from saved version: [timestamp]"* via an informational toast.
   - **Critical Contract**: Resuming a saved draft **NEVER** executes automatic verification or initiates workflow progression.
2. **Revision Request Resumption (Stage 02 $\to$ Stage 01 Rejection)**:
   - When a QA Reviewer clicks "Request Changes" at Stage 02, the question status reverts to `CHANGES_REQUESTED` and returns to Stage 01.
   - When the author opens the draft, the editor renders a prominent, non-dismissible **Rejection Banner** at the top of the form containing:
     - Reviewer Name and Timestamp.
     - Checklist items that failed verification.
     - Mandatory reviewer remarks explaining required revisions.
   - All previously submitted fields remain pre-populated, allowing targeted editing without starting from scratch.
3. **Dirty-State Tracking & Auto-Recovery**:
   - The workbench tracks form modification via an `isDirty` state.
   - If an unpersisted draft exists in local browser storage (due to unexpected crash or browser closure) with a newer timestamp than the server record, the workbench displays an **Unsaved Changes Recovered Modal**:
     - Option A: *Restore Unsaved Changes from Browser Cache*.
     - Option B: *Discard Local Cache & Load Server Version*.
4. **Optimistic Concurrency Control (OCC)**:
   - Every draft record carries an integer `version` field.
   - Upon save or submit, the client submits `{ ...draftData, expectedVersion: currentVersion }`.
   - If another user or session updated the draft concurrently, the server returns `HTTP 409 Conflict` (`STALE_VERSION_CONFLICT`), prompting the user to review concurrent changes rather than silently overwriting.

### 3.1 Stage 01: Question Generation
- **Canonical Route:** `/studio` (`P-04 Question Studio`)
- **Required Data:** Topic taxonomy tree (`topics`, `subtopics`), active draft container (`draftId: dft_<uuid>`), AI prompt configurations, syllabus reference guidelines.
- **Visible Controls:** Topic/Subtopic dropdowns, Production Mode selector, Question Count selector (5/10/15/20 for Mode 1 & 3), Question Stem textarea, 4 Option inputs, Correct Answer radio buttons, Explanation textarea, Mathematical Proof editor, AI Generate button, Save Draft button, Submit for Verification button.
- **Permitted Actions:** `GENERATE`, `EDIT`, `SAVE_DRAFT`, `SUBMIT`.
- **State Specifications:**
  - **Loading:** Split-screen skeleton loader (taxonomy/prompt panel left, schema form fields right). Action buttons disabled with shimmering state.
  - **Empty:** Blank authoring workspace with Topic selector pulsing. Form inputs disabled until valid Topic and Subtopic are selected.
  - **Error:**
    - AI Timeout / Generation Failure: Red alert banner above form with `[Retry Generation]` and `[Switch to Manual]` options. Existing manual inputs preserved.
    - Save Failure: In-place red toast *"Failed to save draft. Check network connection."* Form remains dirty.
  - **Read-Only:** Form controls rendered in disabled/flat typography. Save and Submit buttons hidden. Banner indicates: *"Viewing archived question version. Editing disabled."*
  - **Incomplete:** Inputs with missing or invalid data show inline red validation borders and warning text (e.g., *"Option C is required"*, *"Select a correct answer index"*). Submit button disabled or triggers scroll-to-first-error upon click. Save Draft button remains fully enabled.
  - **Completed:** Form locked; green badge *"Submitted for Verification — Stage 02"*. Action bar renders button: *"View in Verification Queue $\to$"* or *"Create Another Question"*.
- **Draft Resumption:** Navigating to `/studio?draftId=dft_<uuid>` loads the draft document from `question_drafts`, populates all form fields, sets `isDirty = false`, and displays save confirmation. Resumption does NOT auto-verify or trigger Stage 02.
- **Recovery Behavior:**
  - Network save failure retains local in-memory edits.
  - Rejection from Stage 02 displays sticky banner with failed checklist items and reviewer remarks. Clearing remarks occurs automatically upon re-submission.

### 3.2 Stage 02: Question Verification
- **Canonical Route:** `/questions/:id/verify` (`P-05 Question Verification`)
- **Required Data:** Submitted `Question` record (`qst_<uuid>`), version history, mathematical proof payload, author ID (`usr_<uuid>`), 10-point pedagogical audit checklist.
- **Visible Controls:** Dual-pane layout: Question Preview with rendered math formulas (left), 10-point audit checklist toggles (right), Reviewer Remarks textarea, "Request Changes" button (Red), "Approve Question" button (Green), "Terminate" button (Gray).
- **Permitted Actions:** `INSPECT`, `QUESTION_REVIEW:VERIFY`, `QUESTION:APPROVE`, `QUESTION:REJECT`.
- **State Specifications:**
  - **Loading:** Shimmering question preview card and skeleton checklist with 10 placeholder toggles. Action buttons disabled.
  - **Empty:** N/A (Route is parameter-bound). If question ID has no submitted versions: *"No pending submission found for verification."*
  - **Error:** Red alert banner: *"Unable to load question verification record: [error message]"* + `[Reload Review]` button.
  - **Read-Only (Self-Approval Restriction / GAR-02):**
    - Triggered when authenticated actor ID equals `question.authorUserId`.
    - Checklist toggles become disabled. "Approve Question" button is replaced with an amber badge: *"Anti-Self-Approval Active: As author, you cannot verify this question (GAR-02)."*
    - Reviewer may only view the checklist and question text.
  - **Incomplete:** Checklist contains un-toggled criteria (< 10 items evaluated). "Approve Question" button disabled with tooltip: *"Complete all 10 checklist items to approve."* "Request Changes" requires at least 10 characters in remarks.
  - **Completed:** Banner: *"Question Verified & Approved by [reviewer] on [timestamp]"*. Checklist locked in passing state. Action button: *"Advance to Scripting Bay (Stage 03) $\to$"*.
- **Draft Resumption:** If reviewer partially completes the 10-point checklist and leaves, the checklist state is saved in the verification workspace session and re-populated upon returning without losing evaluated criteria.
- **Recovery Behavior:**
  - `REQUEST_CHANGES`: Reverts question status to `CHANGES_REQUESTED`, advances workflow stage 02 $\to$ 01, routes author back to `/studio?draftId=dft_<uuid>`.
  - `TERMINATE`: Formally retires defective question with terminal audit log; halts workflow instance (`wfl_<uuid>`).

### 3.3 Stage 03: Audience Script
- **Canonical Route:** `/videos/:videoId?tab=script` (`P-09 Video Production Workbench — Tab 1`)
- **Required Data:** Approved Question text (`qst_<uuid>`), distractors, solution explanation, current `Script` draft (`scr_<uuid>`), pacing markers (words-per-minute calculator).

- **Permitted Actions:** `SCRIPT:CREATE`, `SCRIPT:EDIT`, `SCRIPT:SUBMIT` (`LOCK_SCRIPT`), `ESCALATE_QUESTION_DEFECT`.
- **State Specifications:**
  - **Loading:** Script editor skeleton with pulsing teleprompter preview card.
  - **Empty:** Blank script workspace with button: *"Generate Initial Script from Question (AI Advisory)"*.

- **Recovery Behavior:** "Report Question Defect" escalates curriculum inaccuracy back to Stage 02, pausing script production until QA reviewer resolves the question issue.

### 4.2 GAR-02 Anti-Self-Approval Invariant Specification
To protect educational rigor and quality standards, BP-CMS strictly enforces the **Anti-Self-Approval Invariant (`GAR-02`)**:

$$\mathbf{GAR\text{-}02}: \quad \text{Reviewer Actor ID} \neq \text{Author Actor ID}$$

```text
 ┌────────────────────────────────────────────────────────────────────────────────────────┐
 │                              GAR-02 ENFORCEMENT POINTS                                 │
 ├─────────────────────────┬──────────────────────┬───────────────────────────────────────┤
 │ Quality Gate            │ Governed Action      │ Invariant Requirement                 │
 ├─────────────────────────┼──────────────────────┼───────────────────────────────────────┤
 │ Stage 02: Verification  │ QUESTION:APPROVE     │ actor.id !== question.authorUserId    │
 │ Stage 07: Final QC      │ VIDEO_EDIT:APPROVE   │ actor.id !== video.editorUserId       │
 │ Stage 09: Social Review │ SOCIAL_REVIEW:APPROVE│ actor.id !== script.authorUserId      │
 └─────────────────────────┴──────────────────────┴───────────────────────────────────────┘
```

#### Server-Side Enforcement Rules:
1. When any approval endpoint is invoked (`/api/questions/:id/verify`, `/api/videos/:id/status`, `/api/social-reviews/:id/approve`), the Express authorization middleware extracts `actor.id` from the authenticated session token and compares it with the target entity's author/creator ID (`entity.authorUserId`).
2. If `actor.id === entity.authorUserId`, the request is **instantly rejected** on the server with `HTTP 403 Forbidden` and error code `FORBIDDEN_BY_SEGREGATION_OF_DUTIES` (or `SELF_APPROVAL_FORBIDDEN` per 09-RBAC Section 9.1).
3. **Universal Zero-Bypass Principle**: The anti-self-approval rule applies unconditionally and equally to all 11 canonical roles, including `CONTENT_LEAD` and `ADMIN`. Administrative status provides zero authority to approve one's own authored artifact.
4. **Absolute Prohibition of Administrative & Emergency Overrides**:
   - There are **zero exceptions, emergency bypasses, break-glass mechanisms, or administrative override protocols** for GAR-02 in BP-CMS.
   - Server-side middleware and domain services unconditionally reject any approval request where `actor.id === entity.authorUserId` with `HTTP 403 Forbidden`, regardless of request flags, claims, or administrative roles.
   - Any client payload attempting to bypass segregation of duties via override fields (e.g., `isOverride`, `bypassGar02`, `confirmedByAdmin`) must be rejected server-side as invalid/forbidden.
   - Operational deadlocks, sick leave, or emergency content progression must be resolved exclusively via legitimate separation of duties: assigning or delegating the review gate to an independent, qualified reviewer or lead.

#### Frontend Presentation Rules:
1. When an author inspects their own submitted artifact at a review gate, the approval button is replaced by an informational badge:
   $$\text{"Anti-Self-Approval Active: As author, you cannot verify your own submission (GAR-02)."}$$
2. The UI never gives the impression that the user is authorized to approve their own work.
3. The author retains full read-only inspection access to verify how their submission appears in the review bay.

### 4.3 12-Step Server Authorization Decision Pipeline
Every protected API request executes the 12-step server evaluation pipeline defined in `backend/infrastructure/security/rbac-evaluator.ts`:

```text
 ┌────────────────────────────────────────────────────────────────────────────────────────┐
 │                      12-STEP SERVER AUTHORIZATION DECISION PIPELINE                    │
 └────────────────────────────────────────────────────────────────────────────────────────┘
   1. Authenticate Actor Context: Extract and verify session token; verify isActive == true.
   2. Resolve Actor Identity & Roles: Map user ID to canonical roles array.
   3. Resolve Requested Capability: Parse required RESOURCE:ACTION token.
   4. Evaluate Capability Possession: Check if actor holds the required token (multi-role union).
   5. Resolve Target Entity Instance: Query Firestore for target document (Question, Video, etc.).
   6. Evaluate Object-Level Access: Check resource ownership / data scope.
   7. Evaluate Segregation-of-Duties (GAR-02): Inviolable check reviewerId !== authorId for APPROVE/VERIFY across all roles (zero bypass).
   8. Evaluate Business & State Preconditions: Check if prerequisites are satisfied.
   9. Evaluate Workflow Transition Rules: Verify WorkflowInstance.currentStage matches operation.
  10. Evaluate AI Human-Gating Constraints (AP-009): Prevent AI from executing gated transitions.
  11. Execute State Mutation & Atomic Audit Log: Persist updates and append AuditEvent.
  12. Return Safe Authorization Result: Return HTTP 200/201 or appropriate standardized error.
```

## 5. Acceptance Criteria & Contract Traceability

### 5.1 Testable Acceptance Criteria
- **AC-T04-01 (Shared Context Grounding)**: Every in-scope production workbench must initialize and maintain a typed `ProductionContext` comprising `topicId` (`top_<uuid>`), `subtopicId` (`sub_<uuid>`), `productionMode`, `questionCount` (where applicable), `contentId` (`cnt_<uuid>`), `draftId` (`dft_<uuid>`), `workflowStage`, `stageStatus`, `assignment`, and `actor`.
- **AC-T04-02 (Direct-Link Hydration)**: Navigating directly to any canonical workbench route with valid query parameters must successfully hydrate session credentials, fetch target Firestore entities, validate workflow stage alignment, and render the correct page state without dropping context.
- **AC-T04-03 (Draft Resumption Independence)**: Resuming a draft via `/studio?draftId=dft_<uuid>` must load saved draft fields into the editor without dirty state, and must **never** automatically trigger Stage 02 verification or advance workflow stage.
- **AC-T04-04 (Save Draft vs. Submit Separation)**: The `Save Draft` action must persist minimal valid fields to `question_drafts` and remain on the current page. The `Submit for Verification` action must execute comprehensive schema validation, require a saved draft, and advance the workflow to Stage 02.
- **AC-T04-05 (15-Stage Page-State Completeness)**: The specification must account for all 15 canonical workflow stages, defining all six essential states (`loading`, `empty`, `error`, `read-only`, `incomplete`, and `completed`) along with draft resumption and recovery behavior for each stage.
- **AC-T04-06 (Zero-Trust Server Authority)**: Frontend button states and page visibility must be treated strictly as presentation. Every backend API endpoint must independently execute authentication, capability checks, and stage precondition validation.
- **AC-T04-07 (GAR-02 Server Enforcement)**: The backend authorization pipeline must reject self-approval requests with `HTTP 403 Forbidden` (`FORBIDDEN_BY_SEGREGATION_OF_DUTIES` / `SELF_APPROVAL_FORBIDDEN`) whenever `actor.id === authorUserId` across Stages 02, 07, and 09.
- **AC-T04-08 (Universal Zero-Bypass GAR-02 Enforcement)**: Server-side GAR-02 anti-self-approval enforcement is absolute across all roles, including `ADMIN`. There are zero emergency, administrative, or audited bypass mechanisms. Any self-approval attempt by an author or administrator must be rejected server-side with `HTTP 403 Forbidden`.
- **AC-T04-09 (Multi-Role Capability Union)**: A user holding multiple canonical roles must possess the union of all capabilities granted by those roles, evaluated atomically without inheritance assumptions.
- **AC-T04-10 (Two-Tier Taxonomy Alignment)**: All workbench contexts and persistence rules must enforce the strictly two-tier taxonomy `Topic` $\to$ `Subtopic`. Any reference to the legacy `Category` concept is prohibited.
- **AC-T04-11 (Traceability & Reconciliation)**: The requirements must explicitly trace to and reconcile with S8-T01 (Question Generation Audit, `dft_<uuid>` prefix), S8-T02 (Workflow Inventory), and S8-T03 (Content Mode Requirements).
- **AC-T04-12 (Zero Implementation Prior to Gate A)**: The repository must contain zero application code, route modifications, or schema changes for S8-T04 until Gate A is formally approved.
